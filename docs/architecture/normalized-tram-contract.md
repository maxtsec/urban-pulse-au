# Normalized Tram history: Phase 1a contract

Status: **Proposed for architect review.** The required field coverage and delivery order were specified on 2026-10-08; row grain, keys and physical schema below remain subject to PR review before implementation. This is analytical history, not the existing city-event/animation contract. Proposed schema version: `tram-normalized-v1`.

## Grain and required fields

Use separate Parquet tables, with explicit schemas even when empty. Keep capture evidence distinct from observations so failures and repeated unchanged feeds remain measurable.

| Table | Row grain | Required columns (nullable source values remain present as columns) |
| --- | --- | --- |
| `captures` | One finalized source capture | `store_id`, `capture_id`, `capture_sequence`, `feed`, `requested_at`, `received_at`, `completed_at`, `outcome`, `http_status`, `failure_reason`, `raw_sha256`, `receipt_sha256`, `feed_timestamp`, `gtfs_realtime_version`, `incrementality`, `entity_count`, `record_key`, `record_id`, `schema_version`, `normalizer_revision` |
| `vehicle_positions` | One VehiclePosition entity occurrence in a capture | Common lineage below; `vehicle_id`, `trip_id`, `route_id`, `start_date`, `service_date`, `start_time`, `direction_id`, `trip_schedule_relationship`, `observed_at`, `received_at`, `latitude`, `longitude`, `bearing`, `speed`, `odometer`, `current_stop_sequence`, `stop_id`, `current_status`, and every nullable source column in the mapping below |
| `trip_updates` | One TripUpdate entity occurrence in a capture | Common lineage; `vehicle_id`, `trip_id`, `route_id`, `start_date`, `service_date`, `start_time`, `direction_id`, `trip_schedule_relationship`, `observed_at`, `received_at`, `trip_delay_seconds`, `stop_update_count`, and every nullable source column in the mapping below |
| `stop_time_updates` | One StopTimeUpdate occurrence within a TripUpdate | `parent_record_key`, parent revision ID and common lineage; `stop_update_ordinal`, `stop_id`, `stop_sequence`, `stop_schedule_relationship`, `arrival_present`, `arrival_time`, `arrival_delay_seconds`, `arrival_uncertainty_seconds`, `departure_present`, `departure_time`, `departure_delay_seconds`, `departure_uncertainty_seconds`, and every nullable source column in the mapping below |
| `quality_issues` | One retained diagnostic for an entity/field | Capture/entity/stop references, fixed reason code, source field and relevant raw capture pin; do not copy credentials or arbitrary exception text |
| `area_memberships` | One observation-to-area evaluation for each selected area | `observation_record_key`, `area_id`, `area_revision`, `static_revision`, `membership` (`inside`, `outside`, `unknown`), `method`, unresolved reason |

Common lineage is `schema_version`, `normalizer_revision`, `store_id`, `capture_id`, `capture_sequence`, `raw_sha256`, `entity_id`, `entity_ordinal`, `record_key`, `record_id`, `static_revision`, `area_revision`. Stop rows also retain `service_date`, `start_date`, `start_time`, `observed_at` and `received_at` from their parent for independent partitioned queries. A TripUpdate with zero stop updates still produces a parent row. Repeated visits to one stop cannot be keyed by stop ID alone. Keep tombstone/deletion entities as capture diagnostics until their analytical treatment is implemented; do not silently drop them or call that capture fully normalized.

## Complete source-field mapping

All source fields in VehiclePosition, TripUpdate and StopTimeUpdate, including their nested messages and experimental fields, have nullable typed columns. Missing source values do not remove columns. Presence flags and source ordinals are additional derived columns, not replacements for source data. Repeated messages use ordered list-of-struct columns with nullable leaf fields; stop updates instead use the child table above. Empty repeated fields are empty lists (protobuf does not distinguish absent from empty repeated fields).

Baseline: official [gtfs-realtime.proto at revision 474750a](https://github.com/google/transit/blob/474750a163088673df718838d4a1bb093391f9af/gtfs-realtime/proto/gtfs-realtime.proto), SHA-256 `8feff2c5499e0ff08777e203e49ef702e07be0a8376b8bb2126add311a709299`. The implementation must pin its descriptor/bindings and test coverage against this baseline, rather than assuming its installed binding includes every field.

| Source message/path | Destination columns / child structure |
| --- | --- |
| `TripDescriptor` in positions and updates | `trip_id`, `route_id`, `direction_id`, `start_time`, `start_date`, `trip_schedule_relationship`; `modified_trip_modifications_id`, `modified_trip_affected_trip_id`, `modified_trip_start_time`, `modified_trip_start_date` from `modified_trip` |
| `VehicleDescriptor` in positions and updates | `vehicle_id`, `vehicle_label`, `vehicle_license_plate`, `vehicle_wheelchair_accessible` |
| `VehiclePosition.position` | `latitude`, `longitude`, `bearing`, `odometer`, `speed` |
| Remaining VehiclePosition scalar fields | `current_stop_sequence`, `stop_id`, `current_status`, `timestamp` (original integer seconds, also decoded as `observed_at`), `congestion_level`, `occupancy_status`, `occupancy_percentage` |
| `VehiclePosition.multi_carriage_details[]` | Same-named ordered list of structs containing `id`, `label`, `occupancy_status`, `occupancy_percentage`, `carriage_sequence`; retain source order, not a map keyed by carriage ID |
| TripUpdate scalar/repeated fields | `timestamp` (original seconds and `observed_at`), `delay` → `trip_delay_seconds`; `stop_time_update[]` → ordered `stop_time_updates` rows with `stop_update_ordinal` and `parent_record_key` |
| `TripUpdate.trip_properties` | `trip_properties_trip_id`, `trip_properties_start_date`, `trip_properties_start_time`, `trip_properties_shape_id`, `trip_properties_trip_headsign`, `trip_properties_trip_short_name`; do not overwrite TripDescriptor columns |
| StopTimeUpdate scalar fields | `stop_sequence`, `stop_id`, `schedule_relationship` → `stop_schedule_relationship`, `departure_occupancy_status` |
| `StopTimeUpdate.arrival` / `departure` | For **each** prefix: `*_delay_seconds`, `*_time`, `*_uncertainty_seconds`, `*_scheduled_time`; retain original Unix seconds in `*_time_unix_seconds` and `*_scheduled_time_unix_seconds` alongside decoded timestamps |
| `StopTimeUpdate.stop_time_properties` | `assigned_stop_id`, `stop_headsign`, `pickup_type`, `drop_off_type` |

Every singular nested message has an explicit `*_present` flag, including trip, modified_trip, vehicle, position, trip_properties, arrival, departure and stop_time_properties. Each enum column has a nullable `*_code` integer companion; explicit defaults and unknown codes are not silently converted to absence. Additive future spec fields require an updated mapping/schema, not implicit dropping.

For every populated field, recursively account for its field number/path, including repeated elements. A present but unmapped field, unknown wire field/extension or enum value, or an unrepresentable value emits a `quality_issues` row (`unmapped_source_field`, `unknown_source_field`, `unknown_enum_value` or `invalid_source_value`) with capture/row/path provenance. That capture is **quarantined and ineligible for expiry**, even if other rows export successfully. Compare descriptor coverage and decoded field presence; a binding that silently discards unknown fields cannot establish completeness. Do not publish a complete normalization result until coverage is proved. Tests must populate every baseline field, plus inject an unknown field and verify the expiry block.

## Types and source semantics

Identifiers/enums: UTF-8 strings (retain enum numeric code as an additional integer where necessary); IDs are never coerced to numbers. Coordinates/speed/bearing/odometer: Float64, finite and within source-defined range. Sequences/counts/delays/uncertainties: signed Int64 where applicable; original protobuf uint64 timestamps use UInt64 before range-checked datetime conversion. Lists/structs retain the typed leaf schema above. Times: Parquet UTC timestamp at microsecond precision; dates: Date; presence flags: Boolean. Use null for absent protobuf fields, preserving explicit zero and absent submessages separately. Invalid source values produce diagnostics with the raw reference; never substitute zero or a current time.

`service_date` is the parsed local service calendar date from TripDescriptor `start_date`; also retain the source `YYYYMMDD` string. `start_time` is a separate service-time string that may exceed 24:00:00. Neither is derived from UTC observation/receipt date. Missing or invalid source service dates stay null with an explicit issue, not a guessed partition. Agency timezone comes from the pinned static feed, not the host timezone.

`observed_at` comes only from the matching VehiclePosition/TripUpdate timestamp. Keep `feed_timestamp` separately; it cannot silently fill a missing entity timestamp. `received_at` comes from the original immutable capture receipt. For the initial DTP trip-updates feed, `observed_at` is expected to be null; this is not a missing-field error. Trip-update freshness uses `received_at` and is labelled **receipt freshness**, not vehicle observation age. If the provider later supplies TripUpdate.timestamp, preserve it without silently changing this freshness definition. Stop rows inherit the parent receipt time. Stop arrival/departure Unix times are source estimates (which may describe past or future events), not independently verified arrivals; preserve both their time and delay even when both are present. Trip-level and stop-level schedule relationships remain separate. Later derived/imputed values require separate columns and a named policy.

These mappings follow the [GTFS Realtime reference](https://gtfs.org/documentation/realtime/reference/) and [GTFS service-time definitions](https://gtfs.org/documentation/schedule/reference/). The references govern source meaning; this document's row layout and identifiers are UrbanPulse proposals.

## Identity, scope and repeatability

Use a version-independent `record_key` as the merge/unique key. Compute SHA-256 of the UTF-8 compact JSON array `['tram-source-row-v1', table_name, store_id, capture_id, entity_ordinal, child_ordinal]` (JSON double quotes, no spaces, no ASCII escaping; UUIDs canonical lowercase; ordinals zero-based integers, absent ordinals JSON null). `captures` has both ordinals null; positions/updates have null child ordinal; stop rows use the source stop-update ordinal. Table name separates message grains. It contains **no normalizer/schema/static/area revision or derived value**. Array order is source wire order, never filtered or sorted order. Source IDs can repeat or be missing without changing this identity rule.

Keep a separate `record_id` = SHA-256 of the same JSON encoding of `[record_key, schema_version, normalizer_revision]` for normalization revision provenance. Current source tables MERGE and assert uniqueness on `record_key`; revision history uses `(record_key, schema_version, normalizer_revision)`. Publish only an explicitly selected normalization revision; do not let an older retry overwrite a newer selected result. Area membership uniqueness is `(observation_record_key, area_id, area_revision, static_revision, normalizer_revision)` and does not redefine observation identity. Quality issues additionally identify field path and reason code. Tests rebuild with a different normalizer revision and assert identical source keys, distinct revision IDs and no duplicate current rows. Entity IDs remain source fields; duplicates within a feed are retained and flagged. Byte-identical records from distinct captures retain distinct capture provenance. Removing repeated provider observations is a later, explicit staging-model rule, not deletion of capture evidence.

Process only finalized captures at a fixed high-water sequence; the read/transform pass does not acquire the collector's exclusive journal lock or modify its checkpoint. Publishing durable downstream state still follows v3 ownership/hold checks; offline export does not bypass those checks. Pin exact capture manifests, source payload hashes, static tram-member hash and both area boundary revisions in the export manifest. Use the accepted Southbank/CBD boundary policy for positions; use pinned trip/stop linkage for updates. Unknown linkage remains unresolved with raw retained. Do not pretend an unresolved record belongs outside the selected areas. Distinct areas share observation rows through the membership table rather than duplicating source records.

Each export describes a half-open UTC receipt interval and its corresponding local-day label/timezone, capture high-water mark, actual coverage, rejected/unresolved counts, input inventory hashes and table schemas. The first one-day export cannot claim 24-hour coverage before that much data exists; a calendar-day export can include explicit pre-activation gaps. Sort table rows by stable record keys and compare values/nulls/precision, not only row counts. Volatile export creation time belongs in the manifest, not the data rows used for rebuild comparison.

## One-off Parquet and upload acceptance

1. First seed the retained timetable archive and deploy/accept the daily [GTFS archive job](gtfs-schedule-archive.md#first-archive-and-export-dependency), including separately approved Terraform. Then run a bounded offline normalizer on the encrypted host data, with no provider calls and no collector restart. Write Parquet and its manifest to a separate encrypted output directory. Preserve the source raw bytes and all unresolved records.
2. Rebuild the same pinned interval and compare every row/column in stable order. Inspect required-field presence, null/zero behavior, midnight and missing-service-date cases, duplicate entities and repeated-stop updates. Pin normalizer/library versions; Parquet binary identity is not assumed across library versions.
3. Perform one reviewed export upload using the existing collector SA and its existing objectCreator capability, without IAM expansion. Keep the [ADR 0018 confirmation protocol](../adr/0018-capture-delivery-and-expiry.md#upload-and-metadata-confirmation): create-only objects, durable pending state before upload, independent service checksums and generation-bound confirmation. The existing scoped `objects.get` remains available only for that accepted confirmation workflow.
4. Use the range-pin amendment below instead of splitting every 32 captures. Group a day by table into Parquet objects, splitting only at the existing 8 MiB object bound; retain a daily inventory and export manifest. Measure resulting object counts/bytes: target a small daily set, not one object per capture. Large tables can still require multiple objects; no unmeasured fixed object-count promise. Record object generations, checksums, row counts and source interval; no recurring upload is enabled by this one-off acceptance.

## Sequence-range upload pins

Requested amendment to the [v3 downstream format](capture-store-v3.md), to be implemented before Phase 1a uploads: use explicitly versioned `capture-upload-pending-v2` records with one inclusive contiguous range `(store_id, first_capture_sequence, last_capture_sequence)`, `capture_count` (exactly last minus first plus one), `inventory_sha256`, inventory format/version and local immutable inventory reference. Keep expected object name, SHA-256, service checksums and size. The old 32 explicit-capture limit applies only to `capture-upload-pending-v1`; do not encode the range inside that format or silently reinterpret it. Keep the 16 KiB pending-record, 32 required objects per capture normalization and 8 MiB object limits; sharding must respect all three or fail before publishing completeness.

Publish/fsync the inventory **before** its pending records. It is canonical UTF-8 JSON Lines sorted by sequence; each compact fixed-order array is `[capture_sequence, capture_id, manifest_sha256, receipt_sha256, payload_sha256, outcome]`, using JSON double quotes, no spaces or ASCII escaping, lowercase canonical UUID/hash strings, null unavailable hashes and a final newline. The pending record carries store UUID and inventory format `capture-inventory-v1`. The SHA-256 covers all bytes. Include **every** finalized sequence in the range, including failures and other feeds; row selection can narrow an output, but cannot weaken its pins. All objects for the day can share the same inventory hash/range. Freeze the high-water sequence; fail on missing, duplicate, reordered or mismatched entries. The inventory is an explicit uploaded artifact too and must be independently confirmed; its pending record refers to its already durable local hash, without a circular confirmation dependency. If an inventory would exceed 8 MiB, split into contiguous subranges with separate hashes, never truncate.

This replaces large inline capture arrays, not per-capture completeness checks. Resolve sequence lookup and verify inventory/receipt/payload identity before marking normalization complete or authorizing expiry. Per-sequence normalization results still identify every required object (including inventory/manifest); each corresponding confirmation must match the range-pending hash. Any changed/missing inventory, unresolved record or unconfirmed object retains the affected raw. Pending state is a pin, never proof of successful normalization/upload. Stream inventory verification rather than materializing the archive or rescanning unrelated captures.

Implement version-aware verifier/recovery and confirmation/expiry-reference readers together before producing v2 pending records. Preserve old v1 records and confirmations unchanged. Older readers must fail closed on the unsupported downstream version; do not install new records under an old verifier. Rollout and crash tests cover inventory publication, pending publication, upload acknowledgement loss, restart, missing inventory, range gaps/hash mismatch and clock rollback. The running capture loop/store is not modified by this documentation PR.

## Alerts delivery phase

**Phase 1c includes `service_alerts` and its child tables, before enabling any raw expiry.** Phase 1a exports positions/updates plus capture outcomes for all feeds; alert payloads stay pinned and are explicitly reported as `product_not_normalized`, not successful empty normalization. Phase 1b's initial mart therefore does not claim disruption coverage. In 1c define/test alert active periods, informed-entity selectors (including trip/service instance), cause/effect/severity, translated text/URLs/images and any populated extension, with source/receipt provenance, area linkage and the same no-silent-loss rule. Its detailed physical schema gets its own review before implementation. Phase 3 joins consume this history; they are not the first stage that saves alerts.

## Raw expiry gate

Keep raw expiry disabled. Required position and stop-level TripUpdate fields must first survive source decoding, Parquet round-trip, upload confirmation and warehouse loading with tests. This is necessary, not sufficient: accepted raw retention, complete normalization of all required products (including alerts), unresolved/quarantine clearance, confirmation and verification holds from ADR 0018 still apply. An export or a successful mart does not alone authorize raw deletion.

Phase 1b then develops the first mart/publication; Phase 1c automates normalization/upload after this contract and one-off path are accepted. [Delivery order](../delivery-plan.md#data-pipeline-priority-track).
