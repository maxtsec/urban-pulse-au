# MAP-02 tram animation input contract

Date: 7 October 2026. Status: **Accepted by the project architect on 2026-10-07 for PR #48**, including the API/clock/identity contract and ADR 0011/0014 amendments. The final review correction limits old-image compatibility to API reads and worker recovery. Implementation and managed rollout remain separate work; progress remains in the [delivery plan](../delivery-plan.md).

Scope: observed/interpolated MAP-02 trams only. **MAP-05 simulated road traffic is outside this contract**; it retains its separate deterministic synthetic inputs and Simulated label under ADR 0011.

## Decisions and implementation prerequisites

The [transport/GTFS foundation](../evidence/map-02-trip-foundation.md) adds nullable trip metadata without changing absent-field receipts, plus an independent trip-complete synthetic fixture and pinned complete shapes selected by Southbank overlap. Real observation matching and its tolerance remain unverified. The current frontend advances 15 scenario seconds after each two-second wait and fetches a snapshot; that produces discrete steps.

| Decision | Accepted rule | Consequence |
| --- | --- | --- |
| Transport metadata | Add a nullable trip descriptor to the existing v1 event | Old events remain readable; absent metadata renders statically |
| API placement | B: separate same-origin animation endpoint, requested only for enabled 3D animation | Static 2D avoids animation history; every response must align with its parent |
| City validity | Parent `valid_until`, independently computable without requesting animation | Both views share known city-state boundaries; unknown validity uses static polling |
| Clock | Integer milliseconds; legacy integer `seconds` remains accepted | Seek and playback use the same canonical instant |
| Playback | With known validity, both views use a continuous millisecond playhead at rate 7.5; server-owned city boundaries and shared position freshness | 2D has static observed markers, no glide and no animation requests |
| Encoding | Per-vehicle `segments` table; observations reference continuity identity | Repeated trip/shape metadata is stored once per continuity segment |

**Implementation prerequisites:** implement and test the compatible public transport-contract addition; preserve original receipt evidence; author trip-complete synthetic observations; verify static GTFS trip-to-shape linkage and its manifest, matching tolerance and model asset licence. Live enablement and provider-field verification remain SRC-02 gates. These prerequisites apply to MAP-02, not completed MAP-01.

The trip descriptor carries `trip_id`, service date/start time where required to identify a repeated trip instance, and nullable `direction_id`, alongside the existing route ID. Resolve `shape_id` through that trip in a pinned static GTFS release; do not invent a producer shape ID or guess from route alone. Matching output belongs to the Location Intelligence view model, not a new observed position or domain fact. Preserve the serialized shape and receipt fingerprint of old events when the new field is absent; adding a default null must not invalidate persisted receipts or make an old retry conflict.

## API placement and alignment

Use **B**, a separate animation response. A (embedding animation in every area snapshot) is rejected because static 2D would repeatedly download and parse unused history. [Encoding measurements](../evidence/map-02-animation-payload.md) compare the former repeated metadata with the segment table; they are synthetic estimates, not runtime performance acceptance.

Both endpoints accept the same area/scenario and canonical parent clock. The animation request additionally identifies the expected `scope_id` from `composition.timeline_id`. The response's `scope_id` and `clock_at` must equal that parent timeline and `clock.at`, after UTC normalization. An active-import change, unsupported contract, mismatch, timeout or failed response cannot be combined with another parent: discard it and use the labelled static parent view. It does not change area assessment or trigger an extra area fetch just to repair animation. Re-pair animation after the next normal area update. Remove queued animation work on seek, scenario change or disabling animation; mark in-flight work obsolete and drain it through the single-request lane below. Reject obsolete replies rather than activating them.

`scope_id` is a timeline identity, not the import ID. Its current inputs are capture identity, scenario policy, boundary revision and `POLICY_VERSION`. Shape revision/hash and animation/display policy versions are checked separately. Never assume that an identical clock alone identifies identical inputs.

### Integer-millisecond query contract

- Add `milliseconds` to area and animation queries: a non-negative integer offset from scenario start, bounded by `MAX_SECONDS * 1000`. Preserve legacy non-negative integer `seconds`, bounded by `MAX_SECONDS`; normalize it by exact multiplication by 1000. Neither supplied means zero. Supplying both is HTTP 422, even when equal. Reject fractional, negative, non-finite or out-of-range values; do not clamp or round user input.
- Use integer milliseconds for the logical playhead, window boundaries, seeks, pause/resume anchors and comparisons. Add `clock.milliseconds` to the parent; retain existing fields for old clients, deriving any whole-second display field by floor division. `clock.at` represents the exact canonical instant, never a rounded whole second. Animation `clock_at` represents the same instant.
- The scheduler converts monotonic elapsed time to integer microsecond ticks at its boundary, then uses integer arithmetic: `p_ms = anchor_ms + (elapsed_us * 15) // 2000`. This is rate 7.5, floored to the millisecond. Do not accumulate rounded frame deltas or float-valued scenario seconds; re-anchor at the exact paused playhead on resume.
- Preserve original receipt/observation timestamps and their precision. Evaluate a millisecond playhead against them without truncating an input into the past. A state transition between representable milliseconds takes effect at the first millisecond at/after it (ceiling), never before its timestamp. Boundary discovery and direct snapshot evaluation must agree on this rule.
- Integer scheduling makes an explicit `milliseconds=p_ms` seek comparable to playback at exactly p_ms. It does not promise that different frame rates sample the same intermediate frames.

### Required clock migration

This is an implementation prerequisite, not a claim about current runtime support. `application.composition.transition_clocks` and `application.city_checkpoints.clocks()` currently round transitions up to whole seconds. Replace both with a shared integer-millisecond boundary calculation covering receipts, validity, coverage, selection and freshness checkpoints. Use integer `timedelta` components, not float `total_seconds()` followed by second rounding. For an offset `u` in integer microseconds, the first representable boundary is `-(-u // 1000)`. A warning effective at 52.4 s must produce 52,400 ms, not 53,000 ms; a 52,500 ms direct seek and playback must agree.

Carry milliseconds through composition, checkpoint scheduling/identity and replay evaluation without converting back to whole seconds. Migrate `urbanpulse.location.city.position_freshness` too: replace float `total_seconds()` with integer timedelta microseconds and integer thresholds. Browser/server parity tests must exercise that real function, not a replacement test helper.

`application.composition.area_event` currently hashes `[timeline, clock.seconds, revision]` for `AreaStatusChanged.id`; `adapters.city_runs` persists the resulting events and publications. Preserve that exact v1 identity and whole-second scheduling for retained v1 runs/outbox recovery. The accepted new identity is `payload_hash(["area-status-clock-ms-v2", timeline_ms, clock.milliseconds, revision])`, using canonical integer milliseconds, never the floor-derived legacy `clock.seconds`. Give new runs an explicit `city-checkpoints-v2` clock/identity version and the accepted timeline policy namespace `southbank-fixture-ms-v2` (through `POLICY_VERSION`); area subjects already include the timeline. The CloudEvents payload type need not change merely to version identity. Here `timeline_ms` means exactly the v2 snapshot's `composition.timeline_id`: `payload_hash([captured.capture_id, asdict(scenario_policy), boundary_revision, "southbank-fixture-ms-v2"])`, using the existing canonical `payload_hash` serialization. It is not a timestamp, run ID, import ID or hash of the request clock. Two v2 clocks share this timeline; the event ID separately includes their exact millisecond clock and revision.

Create v2 runs under new run IDs; never resume an existing v1 run under v2 scheduling, rewrite stored IDs or republish old outbox entries with new IDs. Retained v1 recovery uses its pinned v1 algorithm/image; an incompatible runner refuses before any mutation. Keep v1/v2 results in separate timeline namespaces and select one serving projection rather than merging both as independent incidents. Migrations must preserve existing rows and verify v1 retry/recovery identity plus v2 determinism at whole and fractional clocks. A warning formerly emitted at 53 seconds stays that event in its v1 run; a new v2 run emits at 52,400 ms with its explicitly separate namespace. Test these paths before enabling the endpoint. The [accepted managed cutover/recovery procedure](../runbooks/map-02-clock-migration.md) specifies Job run IDs, revision-local input selection, rollout gates and pinned v1 recovery.

Evidence queries also accept mutually exclusive `milliseconds`/legacy `seconds`. Every `evidence_url` generated for the new parent uses its exact `milliseconds`, with the same scenario and retained scope/import alignment. Evidence at 52,999 ms includes an input received at 52,750 ms; it must not link to `seconds=52`. Mismatched or unavailable retained scope fails explicitly instead of displaying another import's evidence.

### Fixture clock schema prerequisite

Introduce a versioned fixture clock format before writing fractional-receipt tests. Existing bundles with absent clock version (or explicit `clock_version: "seconds-v1"`) retain integer `at_seconds` and `outage_at_seconds`. New `clock_version: "milliseconds-v2"` bundles use integer `at_milliseconds` on every transport position/service, weather and planning frame, and `outage_at_milliseconds` on each applicable scenario/bundle. The selected version requires its own fields and rejects mixed units, missing clocks, booleans, negative/fractional or out-of-range values; do not round. Parent and nested bundles must agree on the version. Keep the fixed scenario start timestamp; durations/limits expressed in seconds remain explicitly named and are converted once.

The shared loader normalizes v1 seconds by exact multiplication to internal milliseconds and preserves the original raw bytes/manifests and version. `adapters.city_import` computes receipt time as `started_at + timedelta(milliseconds=offset_ms)` and retains that exact offset in stored frame/provenance records. Update fixture validators, import/export/load paths, replay filtering (`application.inputs` and transport/service/weather/planning replay), outage gates, timeline/checkpoint discovery and evidence together. V2 bundles have new capture/import identities; never rewrite an existing v1 capture or its receipt fingerprints. Do not fabricate precision when reading v1 fixtures.

The 52,750 ms acceptance fixture uses `clock_version: "milliseconds-v2"` and `at_milliseconds: 52750`; test visibility at 52,749/52,750/52,999 ms through import, reload, replay and evidence. Keep a v1 fixture regression proving unchanged raw hashes, original event receipts and v1-run IDs. This is an accepted fixture-format change and implementation gate, not functionality claimed for today's importer.

### Import-format coexistence

The existing writer uses `NORMALIZER_VERSION = "city-normalizer-v2"`; that version number is independent of the accepted v2 playback clock. **Bump the new writer to `city-normalizer-v3`** for normalized millisecond records. Import identity remains `payload_hash([capture_id, normalizer_version])`, using the actual writer version. Never store the changed format under v2 or recompute an old scope with the new global constant.

The new reader has an explicit version-dispatch registry, separate from its default write version:

| Stored normalizer | Stored clock/decoder | New image read behavior |
| --- | --- | --- |
| `city-normalizer-v2` | Legacy seconds records and their existing observation codec | Verify original envelopes, fingerprints and content hash using the unchanged legacy representation; then adapt seconds to milliseconds in a separate in-memory view, without writes |
| `city-normalizer-v3` | Explicit millisecond records and versioned millisecond observation codec | Verify/decode the millisecond format; reject mixed units |
| Unknown | No decoder | Fail explicitly; never guess a unit or try the current writer |

Update `load(scope)` to dispatch from the stored normalizer tag, not equality with the writer constant. Update `active_scope()` to resolve the named pointer and validate against the caller's explicit readable-version set; it must not hide an existing legacy pointer because the default writer changed, search for a newer import, or activate anything. Revision-pinned serving additionally checks the exact normalizer in its release descriptor. The new image can read both formats for compatibility/inspection; that does not authorize v2 recovery of a v1 run. V1 run execution remains on its pinned v1 algorithm/image.

The v3 writer may normalize either explicitly versioned raw fixture clock through the shared loader; it always writes millisecond normalized records and records both raw clock version and normalizer version. Reading v2 never upgrades it on disk. Version the new observation codec independently; retain the old decoder and validate legacy content hashes before creating an adapted view. The reviewed additive schema change must store explicit millisecond offsets alongside the retained legacy seconds representation (for example, separate nullable columns with exactly one unit per row), never reinterpret or overwrite `seconds`. After that migration, the pinned old image must support API reads of its v2 imports and worker recovery of existing v1 runs, including checkpoint/delivery writes. This does not require old initialization Jobs to work: v1 import/migrate Jobs require `0007_city_checkpoints` and must reject a later DB revision (for example 0008). Test API/worker compatibility with the pinned old image, and verify initialization rejection without bypassing its revision guard.

Required coexistence regression: stage a v3 import beside an active v2 import in one database; verify both through the new versioned reader, the active v2 through the old API and an existing v1 run through its old worker, plus old import/migrate rejection on the newer schema, unchanged old hashes/receipts/IDs, and independent v2/v3 integrity failures. Unknown versions and a release descriptor with the wrong normalizer must fail before serving or mutation. Include `normalizer_version` and codec compatibility in deployment checks and the [rollout proposal](../runbooks/map-02-clock-migration.md).

### Parent snapshot additions

| Field | Meaning |
| --- | --- |
| `valid_until` | Exclusive UTC end of a known nonterminal parent city interval; null for unknown validity or scenario end. Determined by server city boundaries and the 15-second grid, never animation size |
| `terminal` | True exactly at `MAX_SECONDS * 1000`; false at every earlier clock |
| `clock.milliseconds` | Canonical integer offset matching `clock.at`; legacy seconds input remains compatible |
| `position_freshness_policy` | Shared version and thresholds, derived from the server constants described below |

There are three explicit states:

| Parent state | Fields | Client behavior |
| --- | --- | --- |
| Known nonterminal validity | `terminal=false`, non-null `valid_until > clock.at` | Continuous playback within the verified interval; prefetch its successor and apply it only at the boundary |
| Unknown validity | `terminal=false`, `valid_until=null` | Return the valid as-of area snapshot normally; hold its observed view and use the shared polling fallback below |
| Scenario end | `terminal=true`, `valid_until=null` | Apply final transitions, render statically and stop polling/playback |

Unknown validity is not an API error, empty coverage or a terminal marker. For example, future live ingestion cannot predict its next receipt. Both views use the same non-overlapping poll every 2,000 ms of wall time while playback is requested, retaining the last successful as-of snapshot and labelling it with its actual clock. Do not advance a continuous playhead or imply city validity between polls. For fixture playback, each poll requests `min(last_successful_milliseconds + 15000, MAX_SECONDS * 1000)`; failed requests retry that target. Seek still requests the exact chosen millisecond. A future live adapter polls its latest-state query rather than predicting future fixture time; live query/source policy remains outside this fixture contract. Pause stops playback polling. Return to continuous playback only after a nonterminal snapshot supplies known validity; a terminal response stops it entirely.

Animation is `unavailable/validity_unknown` for unknown validity, without failing the parent; the client need not call animation to discover that. Do not manufacture a 15-second validity interval from a polling cadence. Actual snapshot-computation errors remain errors. Unknown/error source coverage may still have known validity in a retained fixture.

### Animation response

Receipt/observation timestamps are UTC RFC 3339. Trip service date/start time retain the GTFS service calendar and source timezone. Coordinates are finite WGS84 longitude/latitude; distances are metres. Retain the parent's capped vehicle order/selection and truncation; do not repeat `max_vehicles` or `vehicles_truncated`. The area `policy_version` remains separate from `display_policy_version`.

| Field | Meaning |
| --- | --- |
| `contract_version` | `tram-animation-input-v1` |
| `display_policy_version` | `tram-display-delay-v1`; display time is playhead minus 30,000 ms |
| `scope_id`, `clock_at` | Exact parent timeline and anchor clock; unchanged across animation-only subwindows |
| `status`, `reason` | `ready` when the aligned response can be evaluated (including mixed/all-static vehicles); `unavailable` for a response-wide failure, unknown parent validity (`validity_unknown`) or a terminal parent (`terminal`), with a diagnostic code |
| `window_start`, `window_end` | Complete animation interval `[c,b)`, with `a <= c < b <= parent.valid_until` for ready responses; a is `clock_at`. End is shortened only by sample/byte bounds |
| `position_input` | `{state, received_at, capture_ids}`; `available`, `unknown` or `error`, independent of service-alert coverage |
| `shapes` | Null or `{revision, sha256, url}` for an immutable same-origin manifest and referenced geometry |
| `vehicles` | One entry per capped parent vehicle when response-ready. Every entry has `vehicle_id`, `source`, `status` (`ready` or `static`) and `reason` (null when ready; diagnostic code when static). Ready entries also have `latest_observation: {source, event_id}`, nullable `startup_observation`, `segments` and `observations`. Static entries omit those animation fields and use the paired parent observation. Empty on response-wide unavailability |

An initial request uses `window_start == clock_at`. To fetch a continuation without changing the area request, keep its `milliseconds`/`scope_id` anchored to the same parent and supply integer `window_start_milliseconds=c_ms` at the preceding animation end. Validate `a_ms <= c_ms < valid_until_ms`. This field is animation-only; `clock_at` remains a, not c. Returned start must equal the requested start. Reject an invalid continuation with HTTP 422 and an incompatible parent scope with HTTP 409. Never follow an animation response that crosses parent validity. Check `parent.terminal` and null validity before interval validation. For unavailable (including `validity_unknown`) or terminal responses use null window bounds, an empty `vehicles` list and a reason (`terminal` at scenario end); no playable interval is claimed. Per-vehicle static fallback does not null the shared bounds or stop healthy vehicles; an all-static ready response can cover the remaining parent interval without animation-only polling.

### Startup reference

The accepted startup exception refers to the first APPLY observation for `(source, vehicle_id)` in the pinned replay scope's complete retained history, not the first sample of a trip, a window or a browser session. This does not claim the vehicle's first observation outside that scope.

Startup eligibility is computed for the **whole canonical city interval** `[L,v)`, using its full display range `[L - 30 s, v - 30 s)`. L is the preceding grid/input/state boundary, not the request anchor a or the animation subwindow start c. Use the received prefix at L, which is unchanged throughout that interval. A seek into its latter half must not skip an earlier unprovable startup requirement.

If any representable display instant in that range precedes every eligible dated observation and the first APPLY record cannot be established from complete retained history, mark the vehicle `static/startup_history_unknown` for the entire `[L,v)`, including later seeks and all continuations. Other vehicles keep their animation. Reevaluate only in the next canonical city interval. A known first observation inside the display range does not remove the interval's startup requirement after the playhead crosses it.

For an admitted vehicle, `startup_observation` is non-null if and only if the whole-interval calculation needs startup fallback and establishes a dated first APPLY observation received by L. Otherwise it is null (no startup needed, missing observation time, or a static vehicle stub). The reference is constant throughout `[L,v)` and included in every ready subwindow even after d passes it; it resolves to exactly one observation in that vehicle's list and counts toward the eight-sample/byte limits. Deduplicate it with bracket/latest observations. Reserve it during whole-interval admission, never substitute a trip/window's first sample to fit. The renderer actually uses it only while d precedes its observation and no eligible dated hold exists; later frames use ordinary brackets/holds. Missing-time fallback remains separately labelled Observed. Reconstruct the same interval decision on direct seek, independently of browser visits.

### Observations

Each observation contains:

| Field | Meaning |
| --- | --- |
| `source`, `event_id`, `revision` | Original accepted event identity/revision; `(source, event_id)` identifies the sample |
| `capture_ids` | Original unique capture references, unchanged by redelivery |
| `observed_at` | Provider observation time, nullable; missing time disables interpolation |
| `received_at` | First successful application receipt. Fixtures use `started_at` plus the first accepted frame's normalized millisecond offset (v1 seconds multiplied by 1000; v2 `at_milliseconds`); live support requires retained original receipt evidence. Never request, replay or retry time |
| `longitude`, `latitude` | Original observed coordinates |
| `shape_match` | `{status, continuity_id, distance_m}`. Status is `matched`, `unmatched` or `ambiguous`; unmatched/ambiguous samples have null reference/distance |
| `trip` | Omitted for matched samples (resolved from `segments`); mandatory inline object for unmatched/ambiguous samples: `{trip_id, service_date, start_time, route_id, direction_id}`. Preserve known producer fields and use null for missing values |

Each vehicle's `segments` is an object keyed by `continuity_id`. Each value stores `{trip_id, service_date, start_time, route_id, direction_id, shape_id, segment_id}` once. `segment_id` names a complete directed source shape component; the table key names a trajectory continuity segment, and the two are not interchangeable. Include only entries referenced by returned observations. Every matched observation resolves exactly one key in its own vehicle table and has a finite non-negative `distance_m` within that component. Invalid linkage or dangling/cross-vehicle references cause that vehicle to use `static/invalid_linkage`; never infer a missing entry. An unparseable envelope invalidates the response. The server constructs typed objects/maps and serializes once; serializer tests must assert unique object keys at every depth using a duplicate-aware decoder. The browser may use ordinary `JSON.parse` plus schema/linkage validation; this contract does not claim it detects duplicate keys. Conflicting entries must be rejected before constructing server maps, not silently overwritten. Unmatched/ambiguous observations remain in history as continuity breaks and observed fallbacks, with inline trip/route metadata as well as their original event references. Inline trip identity does not make an unmatched sample interpolatable: keep its continuity break, never bridge an ambiguous instance, and distinguish an old-trip hold from an unmatched fallback.

A matched sample identifies an unambiguous trip instance and directed shape component from `shapes.revision`. Nullable GTFS fields stay null; an absent value cannot bridge an ambiguous trip instance. The [source register](../source-register.md#tram-track-geometry-map-02) owns release, linkage and matching-tolerance verification.

The manifest records source ZIP/release and fixture hashes, coordinate/distance conventions, matching algorithm/version and accepted tolerance, and included/excluded IDs/counts. Each shape has contiguous components keyed by `segment_id`, with all original ordered vertices and non-decreasing cumulative metre distances from the original shape origin (coincident consecutive vertices have equal distances). Architect amendment accepted on 2026-10-07: select shapes with positive-length Southbank overlap and retain each entire shape, including outside-area spans; never cut continuity at an area boundary or join distinct source shapes. A zero-length polyline edge contributes no travel distance and is skipped when locating an interpolated distance. Shape availability does not expand area membership or make out-of-area observations eligible for an area result. `continuity_id` identifies an accepted trajectory segment, breaking on trip/direction/shape/component changes, missing time/match, non-increasing observation times or decreasing distances. Derive it from the segment's first accepted event and linkage, so later receipts cannot rename an earlier segment. Illustrative fixture tracks are not verified matching evidence.

## Continuous clock and complete windows

For a nonterminal parent with known validity only, let **a** be its clock and **v** its non-null `valid_until`. Terminal and unknown-validity parents use the separate rules above. Independently of animation, the server chooses v as the earliest boundary strictly after a among the next 15-second scenario grid boundary, scenario end, original input receipt, authored outage, warning/service validity, domain-coverage expiry, membership or vehicle selection change. Apply transitions exactly at a before returning the new snapshot. Position age/freshness transitions alone do not end this interval: the client uses the shared policy below. Both 2D and 3D can discover v using only the parent endpoint.

For a ready animation request starting at **c** (initially a), begin with **b = v**; shorten b only as required by the eight-sample or byte limits. Never shorten parent v for animation size. All observations in every continuation have `received_at <= a`. Select enough accepted history to evaluate every display time in `[c - 30 s, b - 30 s)` without crossing a receipt boundary or omitting a discontinuity. Only the active window may drive rendering. A queued successor may contain later receipts eligible at its own anchor, but those records remain isolated until activation under the prefetch rules below.

The parent domain facts, latest observed coordinates and membership remain valid on `[a,v)`. Position freshness/visibility are evaluated at the playhead; parent values describe a. A vehicle whose required history cannot fit at the requested instant uses its labelled static fallback under the allocation rule below; it does not shrink city validity or disable other vehicles. A client with a valid ready animation advances only below `min(valid_until, window_end)`; static 2D or animation fallback uses valid_until alone.

### Bounded prefetch and boundary activation

For retained fixtures with known validity, prefetch towards **2,000 ms of wall-time coverage**, equivalent to 15,000 scenario milliseconds at rate 7.5: target `min(p_ms + 15000, scenario_end_ms)`. Follow successive parent validity boundaries until queued coverage reaches that target, a terminal/unknown-validity parent stops discovery, or the bounds below are reached. This may require several short city intervals; do not stop merely because one successor was fetched. Refill as the playhead consumes the queue. Both views discover the same parent chain; 3D additionally queues animation windows paired with those parents and continuations. Acquiring these responses never applies their inputs early.

Use separate fixed capacities: at most **6 queued parent responses and 6 queued animation responses** (12 total, excluding the active pair), at most **2 MiB of serialized queued parent bodies** and **6 x 256 KiB of serialized queued animation bodies**. Parent limits are identical in 2D/3D and cannot be consumed by animation. Count in-flight responses against their respective slots; streamed responses that cannot fit the remaining byte budget are discarded without activation. These are raw-body bounds, not JavaScript heap guarantees; measure parsing/geometry overhead separately. A queue limit is a reason to stop prefetch, not skip a boundary or exceed the budget.

Coverage is time-based even when intervals are short: for example 52,400 and 52,750 ms successors may both be prepared before either activates. If network throughput or the six-parent cap cannot reach the target, report the actual queued duration and refill/buffer as necessary. Initial playback may buffer while filling; a bounded queue cannot promise uninterrupted playback for arbitrarily dense boundaries. Unknown validity retains the shared polling fallback.

Keep active and queued state separate. Queued responses cannot affect markers, labels, panels, counts, accessible lists, evidence links, events or the active projection before their boundary. At v, atomically activate the validated successor parent and its paired animation (or an explicitly labelled static fallback). At b<v, activate only the validated continuation; the parent stays unchanged. Receipt eligibility is evaluated against each response's anchor, then rendering is gated by the active playhead. This changes acquisition timing, not the no-future-rendering rule. The terminal parent may be prefetched, but is not displayed until scenario end.

### Client request concurrency and database acceptance

One shared request scheduler per viewer tab permits **at most one in-flight city-data request**, covering area, animation, evidence and API geometry queries. Static model/shape assets are outside this database-request lane. Prioritize foreground seek/evidence, then the earliest missing parent boundary, then animation for the earliest uncovered playhead; after that, extend parent coverage to the horizon and fill animation coverage. Foreground actions invalidate queued work but do not launch another request alongside an obsolete one. Mark an in-flight request obsolete and drain it before admitting its replacement; cancellation/timeout does not prove that server-side SQL has stopped.

Coalesce identical keys `(endpoint, scenario, scope_id, clock_ms, window_start_ms)` and validate a playback-generation token on activation. Seek, rewind or scope/scenario change discards queued responses; late obsolete replies cannot become active. Pause stops new speculative requests; valid completed queues may survive resume. Disabling 3D removes only animation work. Scope changes require reinitialization at the boundary. Responses returning 503/429 or timing out suspend speculative refill and retry through the same lane with capped backoff (1, 2, then 4 seconds; respect a longer Retry-After). Foreground navigation still uses the lane; no automatic fan-out retries.

Keep [ADR 0012](../adr/0012-managed-demo-resource-profile.md)'s resource envelope unchanged: one API process per instance, pool 2, overflow 0, checkout wait 1 second, concurrency 4 and max 2 instances. The per-tab limit reduces one viewer's demand; it does not guarantee aggregate capacity, cancellation of server work or equal load distribution. Two tabs/viewers can occupy both connections on one instance, and readiness shares that pool. Do not assume four connections across two instances removes contention. Each request must avoid nested/concurrent database checkouts; verify this during implementation.

Before accepting prefetch, measure 1 and 2 simultaneous 3D viewers through IAP, forced concentration on one instance, normal two-instance distribution, rapid seeks, evidence clicks, short-interval queues and readiness traffic. Record per-instance sessions/checked-out connections, request and checkout-wait p95, 503/429 rate, prefetch coverage, buffered time and parsed memory. The [resource plan](demo-cloud-resource-plan.md#connection-envelope)'s replacement envelope/role caps still apply. Readiness failures must not drive liveness restarts. If contention appears, reduce speculative refill/request work and retest; changing pool, checkout wait, Cloud Run concurrency/instances or audience capacity needs separate review. The current budget does not establish a multi-viewer latency guarantee.

A ready queued pair crosses the boundary without deliberately pausing or resetting the timer. Buffer only if the next parent is missing at v; freeze the logical clock and exclude waiting time by re-anchoring on resume, rather than catching up across unverified intervals. If the parent is ready but animation is late/failed, apply the parent on time and use its labelled static view; animation can resume only from a valid window covering the current playhead. At b<v, a late continuation likewise uses static fallback without blocking area progression. Discard windows already passed; do not apply their old frame on arrival. Unknown validity uses the polling fallback, with no speculative next-clock request. An invalid/non-advancing window never starts a request loop.

Measure parent and animation latency, missed-prefetch boundaries, buffered wall time and memory through the managed IAP path during implementation. With responses arriving before their boundaries, tests must show no forced stop at each 15-second grid point; delayed replies may cause observable buffering, not a claim of guaranteed zero stalls. Test clustered 52,400/52,750 ms boundaries within the time horizon, queue-cap saturation, the one-request lane and future warnings/receipts prefetched at v are invisible at v-1 ms and visible exactly at v, plus pause/seek/rewind, scope changes and terminal activation. Timing numbers are acceptance evidence to collect, not estimates asserted here.

### Position freshness within a window

The accepted **parent snapshot** field, shared by 2D and 3D, is `position_freshness_policy: {version, stale_after_seconds, expired_after_seconds}`. The 120/300-second fixture thresholds are already accepted, but **`southbank-position-freshness-v1` is an accepted wire version name, not implemented**. In the future serializer, derive `stale_after_seconds` and `expired_after_seconds` directly from `POSITION_STALE_SECONDS` and `POSITION_EXPIRED_SECONDS` in `urbanpulse.location.city`, the same constants used by `position_freshness` and the server's checkpoint scheduling. Review/version any threshold change and keep serialization, server evaluation and checkpoint timing consistent; do not maintain independent frontend or serializer constants. This adds a versioned public view contract without approving a live TTL.

At playhead p, apply the policy to each vehicle's **latest accepted observation** named by the parent, never an older sample chosen for the delayed pose. Null or future `observed_at` means `unknown`; otherwise compare elapsed integer microseconds against the supplied integer-second thresholds multiplied by 1,000,000: `expired` at/after the expiry threshold, `stale` at/after the stale threshold, and `current` otherwise. Expired vehicles are hidden on the map; the last-known list remains. Stale vehicles are static and dimmed. Both views use the same evaluator for labels, map visibility and any visible-marker tally. Preserve the server's area assessment, source coverage, membership, `positions_total`, cap and truncation: those do not depend on this position-age display calculation.

Preserve original timestamp precision. The browser must use a strict custom UTC RFC 3339 parser accepting zero to six fractional digits, padding the fraction to microseconds and returning integer microseconds (`BigInt`); `Date.parse` is not an authoritative parser for this calculation. The server uses integer datetime/timedelta components, not float seconds. Canonical view timestamps use `Z`; unsupported precision/invalid dates fail validation rather than silently rounding. Compare `p_ms * 1000` to parsed timestamps and integer thresholds. An observation at 0.0004 s is still current at p=120,000 ms and becomes stale at 120,001 ms. Preserve the original timestamp for evidence and use the same precise parser for receipt gating and interpolation brackets.

Validate a supported policy version and finite ordered integer thresholds (`0 <= stale < expired`). Missing/invalid/unsupported policy prevents continuous playback; retain the static server snapshot with an explicit unavailable reason rather than guessing values. Verify browser/server parity at each threshold and immediately before/after it, including null/future timestamps. With 100 staggered vehicle age transitions and no domain/input changes, the parent 15-second interval must remain intact and trigger **zero freshness-only requests**. Other data boundaries may still shorten it; measure those requests and buffering in MAP-02.

### Playhead scheduling

The scheduler above advances an explicit millisecond playhead at rate 7.5. Render `frame(p_ms, window)` at `d_ms = p_ms - 30000`. Meshes never integrate velocity or read wall time independently. Elapsed time schedules the logical clock; it is not another source of position data.

At a boundary, activate queued validated data before committing its frame. Continue without a deliberate pause when ready; buffer and hold the last valid frame only if the next parent is missing. Late/failed animation uses the valid parent's labelled static fallback. Never advance city state beyond valid_until while its next parent is missing. Pause freezes p_ms; resume anchors the timer there. Seek/scenario change invalidates queued/obsolete replies, schedules the exact target milliseconds through the shared request lane and resets the timer. Direct seek and playback must produce the same pose, truth label and visible city state at p_ms, independent of request start time and sample chunking. At scenario end render the final snapshot statically. Hidden-tab resume must not jump across unverified boundaries.

### 2D playback

With known validity, both views use the same continuous millisecond playhead, city boundaries and area-request parameters. Unknown validity uses the same static polling fallback in both views. MAP-02 replaces the former 15-second stepped 2D clock and 1.5-second glide. 2D markers remain at the latest received observed coordinates until a new parent supplies an observation; freshness and visibility update from the shared policy at p. 2D never requests animation history. Clock text and progress describe the logical playhead, including fractional time when exposed; pausing/seek never snaps back to the parent anchor. A receipt at 52,750 ms refreshes the parent in both views, not at the next 60,000 ms grid point.

## Selection, discontinuities and delayed delivery

1. Reconstruct the accepted receipt prefix at a using the existing revision guard. Only original **APPLY** outcomes enter animation history. Duplicate/conflict/rejected/**SUPERSEDED** attempts add no sample. An earlier APPLY remains history after a later accepted revision; that is different from an incoming old revision rejected as SUPERSEDED.
2. A delayed observation becomes usable after receipt **only if its event is APPLY**. For example, revision 2 arriving after accepted revision 3 is excluded; revision 4 carrying an older observation time can apply but breaks continuity. This contract does not introduce out-of-order historical ingestion or change `compare_revision`.
3. Select history around the **display interval**, retaining relevant old and new trip segments. Include the last dated observation at/before its left edge, all observations inside it, the first dated observation at/after its right edge, and the latest accepted observation needed by the parent. Retain continuity markers and any static fallback required by missing timestamps. Deduplicate by `(source, event_id)` and use canonical accepted revision order. Do not select only the latest trip.
4. For each d, interpolate only between consecutive bracketing observations with the same verified `continuity_id`. Across a trip/shape/gap break, hold the last eligible observed position at/before d; switch to the new segment only when d reaches its first observation. Never substitute the latest trip's first sample for that hold.
5. Use ADR 0011's accepted startup amendment only for the scope's first observation as defined by `startup_observation`, with the truth labels below.
6. Stale/expired rules use p and the server-supplied position-freshness policy above. Unknown/error position input stops motion; other domains do not gate it. A failed shared shape load/hash verification or envelope validation uses response-wide labelled static fallback; vehicle-specific validation falls back only for that vehicle. Both preserve the city assessment and accessible list.

### Two-observation constant-speed interpolation

Architect clarification accepted on 2026-10-07: each rendered segment uses **two consecutive eligible observations**, on the same verified trip/shape/component/continuity segment. For their observation times `t0 < t1` and cumulative path distances `s0 <= s1`, render at display time `d` using `s(d) = s0 + (s1 - s0) * (d - t0) / (t1 - t0)`, only within the inclusive bracket. Locate that distance along the retained shape polyline. Equal distances mean zero speed. Speed is constant within each bracket and may change at the next bracket; do not add acceleration, easing, traffic prediction or one globally chosen speed for every trip. Equal elapsed fractions traverse equal path distances, including through unevenly spaced vertices and bends.

Both observations must already be receipt-eligible under the parent/window rules. Never use an unreceived point or extrapolate past the latest eligible point; hold/fallback, stale and continuity-break rules still apply. Use the **Interpolated** truth label. This estimates a path between observations; it does not claim constant physical vehicle speed. The bounded window may retain several consecutive pairs (up to the existing eight-observation cap); the renderer evaluates only the pair bracketing d. Keeping that window avoids changing the sample/prefetch contract merely to express a two-point interpolation algorithm.

The selected live collection cadence is 60/120/60 seconds (positions/updates/alerts). Sampling cadence does not change the accepted 30-second fixture display-delay version or live freshness gates. Wider gaps or late producer observations may leave no bracket and produce holds; constant-speed interpolation does not guarantee uninterrupted motion. Any live display-delay adjustment needs its own measured acceptance.

### Truth labels

Labels describe provenance, not whether an object happens to be moving. The legend must say: "Interpolated positions: 30-second display delay. Observed holds/fallbacks: recorded position and timestamp."

| Rendered case | Label and displayed time |
| --- | --- |
| Within a valid same-segment bracket, **including either observation endpoint** | **Interpolated**, display time d and both supporting observation times; retain this class when paused, buffering or the two positions coincide |
| An isolated observation with no valid bracket, rendered statically | **Observed**, that observation's actual timestamp and hold/fallback reason |
| Holding the old trip's last position across a trip/shape break | **Observed**, the held observation's timestamp; never the next trip's timestamp |
| Holding the latest received position because d is later than it | **Observed**, that latest observation's timestamp; no extrapolation claim |
| Startup, missing-time, unmatched-shape or stale/error static fallback at an observation | **Observed**, the selected observation's timestamp or "observation time unknown"; explain the fallback reason |

Keep **Interpolated** throughout a supported continuous trajectory, including exact observation times. At a shared endpoint, prefer the following valid bracket when available, otherwise the preceding valid bracket; both use the same label and endpoint coordinate. Use **Observed** only for an observed-position hold or fallback, not for a single frame merely because d equals a sample time. This classification depends on the valid bracket at d, not the previous rendered frame or browser frame rate.

Freezing an interpolated frame during a network wait does not relabel it Observed; the playhead and its existing label remain frozen. Expired/hidden positions retain their observation metadata in the accessible list. At p=75/d=45 with X observed at 30 and Y at 60, the held X position is Observed at 30; at p=90/d=60, Y is Observed at 60 if it still has no valid same-trip bracket; with a received second Y sample forming a valid bracket, it is Interpolated even at that endpoint. Interpolation resumes only with a valid bracket within Y.

### Vehicle-local fallback and payload allocation

Accepted hard limits are the parent cap (currently 100), **8 observations per ready vehicle** and **256 KiB of uncompressed compact UTF-8 response JSON**, including alignment, statuses, segment tables and metadata. A normal trip change can exceed the byte limit even with four samples per vehicle. Window shortening cannot solve overflow in the history already required at its start.

Separate response failures (scope mismatch, invalid envelope, unavailable shared geometry) from vehicle failures. A missing startup history, invalid vehicle linkage, sample limit or byte allocation failure returns only that vehicle as `static`, with `startup_history_unknown`, `invalid_linkage`, `sample_limit` or `byte_limit`. Use the paired parent's observed location/time and an **Observed** label/reason; never label it as delayed interpolation. Retain all capped vehicles through these small stubs; do not discard an interior sample from a vehicle still labelled ready.

Allocation must be deterministic for seek and playback, not first-come network order. Use the canonical city interval containing p (bounded by the same grid/input/state transitions as parent validity, independently of the requested anchor). Use only history received by that canonical interval's left boundary; no later receipt is eligible. Apply startup eligibility over the full canonical display interval first, including its fixed reference reservation. For each eligible vehicle determine the maximum complete byte/sample requirement of any minimum one-millisecond window within that interval, retaining inclusive brackets, breaks, latest and startup references. This admission requirement is independent of animation subwindow selection. Reserve the full response envelope (including the maximum encoded clock/bound lengths within the interval) plus static stubs for all parent vehicles; in canonical parent order admit each eligible vehicle's complete requirement if its incremental reservation fits, otherwise retain its stub and continue to later vehicles. The admitted set and reasons stay fixed within this city interval for direct seeks and continuations. Source changes at its end trigger fresh admission. Bound and measure this calculation during implementation.

For admitted vehicles, start b at parent validity and shorten it only when the combined complete histories for `[c,b)` exceed the byte/sample bounds. Do not change admission merely because a longer window needs more samples; first shorten the window. The reserved minimum-window histories guarantee a nonempty representable window; test this explicitly. Serialize and check the actual whole body, including static stubs. Only if even the all-static envelope cannot fit may the entire response use `unavailable/envelope_limit`. If all vehicles are static, return ready with b=v and no animation-only continuation. Report b faithfully and never change parent validity. This trades some vehicles' animation detail for bounded payloads while preserving the rest; record ready/static counts in acceptance evidence.
