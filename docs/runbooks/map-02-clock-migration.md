# Proposed MAP-02 clock rollout and v1 recovery

Status: **Proposed with PR #48; requires architect approval and implementation before execution.** Architecture authority: the [proposed ADR 0014 amendment](../adr/0014-managed-demo-continuous-delivery.md#proposed-map-02-serving-and-compatibility-amendment) and ADR 0011 decision table. This procedure adds deployment gates to the [animation contract proposal](../architecture/tram-animation-input-contract.md). It authorizes no cloud apply, Job execution, input activation or traffic promotion. Use the existing [managed Job](managed-demo-jobs.md) and [CD](managed-demo-cd.md) approval flows.

## Current behavior and required selectors

`infra/demo-jobs` owns the managed worker definition, including a fixed `worker_run_id`, image digest and import pin. Serving CD owns Cloud Run revisions; publishing a new image does not itself safely migrate worker runs. The current API loads `CityInputStore.active_scope()` and recomposes area snapshots; it does **not** select the worker's persisted result by run ID. Therefore changing the Job run ID alone cannot select a serving projection.

Before v2 rollout, implement and test these selectors:

- A release compatibility record pins `import_id`, `normalizer_version`, readable observation-codec versions, `policy_version`, `run_version`, fixture `clock_version`, schema revision and API/web image digests. It identifies the projection the revision can serve.
- A revision-local API import pin (proposed setting `CITY_IMPORT_ID`) selects that exact retained import through `store.load(pin)`, without changing the shared active pointer. Its policy comes from the pinned application version and must match the release record. Area, animation, evidence and boundary access share this selector. Missing/incompatible pins fail readiness; never fall back silently to the latest import.
- A v2 staging-import mode verifies and persists an import without making it active. The current import Job activates its successful import, so it cannot perform this step unchanged. Add/review the staging behavior before uploading a different-clock fixture into the shared database.
- The CD compatibility check compares these versions as well as schema/import identity. A normalizer/clock/policy/run/codec compatibility change is an explicit migration gate, not an ordinary automatic candidate. Resume routine CD only after a new compatible baseline is recorded.

Keep the v1 active import and its serving revision intact throughout staging. A v2 worker may populate its isolated run/results, but the API still derives area data from its revision-pinned inputs; it must not union v1/v2 result histories.

## Normalizer coexistence gate

Playback v1 currently stores imports tagged **`city-normalizer-v2`**; playback v2 proposes writer **`city-normalizer-v3`**. Before staging, implement the contract's version-dispatched readers, and decouple readable versions from the default writer. `load(scope)` verifies the persisted row with its own decoder/hash representation before converting a legacy offset in memory; `active_scope()` validates the selected pointer against an explicit readable-version set rather than equality with the writer constant. The v1 pointer stays valid for the new reader and the pinned old image.

New import IDs include writer v3; old v2 IDs are never recomputed or updated. Record source fixture clock version, normalized format and codec separately. The additive schema must preserve old-image reads/writes, with explicit millisecond storage rather than reusing the meaning of `seconds`. Unknown versions and incompatible release descriptors fail closed. Supporting legacy reads in a new image does not authorize running old checkpoints under new identity rules.

Rehearse both imports coexisting in the same database: new-image load of v2/v3, old-image load and retry of v2, unchanged old hashes/receipts/events, active-pointer resolution, independent integrity failures, and candidate/rollback readiness against their own format pins. If any fails, do not stage/apply a managed cutover. Include the reader registry and schema compatibility in the retained release evidence.

## Prepare and execute the v2 cutover

1. Record the v1 worker Job definition, exact API image manifest digest, import/run IDs, `city-checkpoints-v1`, `southbank-fixture-v1`, schema revision, secret versions and previous serving revision/digests. Retain that image and inputs through the rollback/recovery period; registry cleanup must not remove them. Verify compatibility with any proposed additive database migration in a disposable rehearsal.
2. Build and test the v2 fixture loader, integer clocks and namespaced event IDs. Record the new capture/import identity, writer `city-normalizer-v3`, codec version and `milliseconds-v2` fixture version, after the coexistence gate passes. Prove existing v1 raw captures, area-event IDs, checkpoints and outbox records remain unchanged. Do not repurpose a stored `seconds` column as milliseconds; any new unit storage needs its reviewed migration and compatibility tests.
3. Stage the v2 import without activating it. Select a new stable worker run ID from the import and clock generation, for example `demo-city-ms-v2-<full-import-hash>` (80 characters, within the existing 100-character bound). Record that exact ID; retries of this scope/generation reuse it. A source SHA change alone does not create another run. A changed import or clock generation does.
4. Prepare a saved Terraform plan for `infra/demo-jobs` changing the worker image, import pin and `worker_run_id` **together**. Confirm no previous mutation execution is active and no legacy writer is connected. Review target units/arguments: the current `--seconds 360` is an explicit seconds CLI limit, not a millisecond checkpoint identity. Preserve that compatibility or introduce an explicitly named millisecond argument; never pass 360 as milliseconds by accident. Definition apply and Job execution each follow the existing approvals; no ad hoc argument overrides.
5. Execute the pinned v2 worker after approval. Verify the v2 run completes, its namespace/identities match the release record, and v1 rows/publications have not been rewritten. Collect execution/resource evidence as required by the managed Job runbook.
6. Create a zero-traffic candidate with v2 API/web digests, the exact `CITY_IMPORT_ID`, `city-normalizer-v3` import format, `southbank-fixture-ms-v2` policy and `city-checkpoints-v2` compatibility record. Read back its pin and verify scope, clock, animation/evidence alignment and fixture version. The v1 serving revision must continue reading its original input and policy. If the current deployment code cannot express these selectors, stop rather than changing the global pointer to make the candidate work.
7. After candidate acceptance, promote the exact revision through the protected flow. Record both new and previous descriptors. Traffic promotion selects the serving implementation/input pair; it does not alter old worker identities or delete inputs. Never mix result streams across generations.

## Recover a retained v1 run

1. Inspect the existing run and its input scope/version, checkpoints, pending deliveries and error/dead-letter records using [checkpoint controls](city-checkpoints.md) and [event recovery](event-recovery.md). Retain the original run ID and import; do not create a replacement v1 run or reinterpret its target unit.
2. Verify the original import remains tagged `city-normalizer-v2`, the pointer/pin still selects it, and the recorded v1 image digest is available and compatible with the current schema and grants. If compatibility was not rehearsed, stop and use an approved isolated restore/recovery target; do not guess that an old image can write a new schema.
3. Quiesce mutation Jobs/legacy writers. Prepare a reviewed Job-definition plan restoring the recorded v1 digest, original import/run IDs, explicit seconds target and existing restricted identity/secret versions. Use the current managed Job ownership and approval process; do not make an unmanaged production Job or override execution arguments. This recovery does not change the serving revision/import selection.
4. After separate definition/apply and execution approvals, rerun the exact v1 request. Resolve recorded errors/dead letters through their existing reviewed procedure. Verify unchanged event IDs, receipt/publication identity and terminal completion; do not rewrite history to manufacture success.
5. Restore the reviewed v2 Job definition before later v2 executions. Any serving rollback separately promotes the retained v1 revision only after its schema/input compatibility is confirmed. Do not roll back schema or the shared import pointer as a side effect of worker recovery.

## Required rollout evidence

Retain v1/v2 release descriptors, reviewed Job plans, execution IDs, immutable image digests, new run ID, unchanged v1 identity checks, candidate import/policy readback and promotion/rollback records. Rehearse a v1 retry after v2 staging and verify v1 serving remains unchanged. These are implementation acceptance requirements, not completed managed tests in this documentation PR.
